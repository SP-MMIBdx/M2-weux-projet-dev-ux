## 2. Comment les fichiers travaillent ensemble

```text
Live Server fournit les fichiers via HTTP
                   ↓
Le navigateur lit fluxparrain.html ou login.html
                   ↓
Le lien stylesheet charge assets/css/style.css
                   ↓
Le navigateur construit les éléments HTML, y compris les fallbacks
                   ↓
Le script en fin de body charge et exécute assets/js/main.js
                   ↓
loadPartial recherche un conteneur par ID
       ├── absent : return, aucun chargement de ce fragment
       └── présent : fetch → contrôle HTTP → lecture → innerHTML
```

Le serveur ne fait pas tourner notre JavaScript : le navigateur l’exécute. Les URLs de `fetch` sont ici relatives au document, pas au dossier `assets/js/`.

Dans le flux parrain, `site-header` et `site-footer` sont présents : les deux fragments sont demandés. Dans la connexion, seul `site-header` est présent ; le footer garde ses classes CSS mais n’a pas l’identifiant ciblé. Il reste donc local et ne reçoit pas « Mon profil ».

## 3. Lire le HTML sans confondre structure et apparence

- `head` contient les métadonnées, le titre d’onglet et le lien CSS ; `header` contient l’introduction visible de la page.
- `body` contient l’interface. Un seul `main` représente le contenu principal.
- Une `section` regroupe un sujet et possède un titre ; un `article` représente une demande autonome ; un `div` est un conteneur générique.
- `h1`, `h2` et `h3` expriment une hiérarchie, pas des tailles choisies pour leur apparence. Le CSS contrôle la présentation.
- `class` sert ici à réutiliser des styles. `id` identifie un élément unique pour les associations de labels, ARIA ou JavaScript.
- `aria-labelledby` prend un identifiant : utiliser le texte de l’élément référencé comme nom accessible. `request-1-title` est un identifiant technique ; « Lucia » est le texte visible illustratif.
- `aria-label` donne directement un nom accessible ; `aria-describedby` référence un texte descriptif complémentaire.
- Un lien `a` navigue ; un `button` déclenche une action. `disabled` empêche l’interaction avec les actions encore indisponibles ; l’opacité seule ne le ferait pas.
- Les fragments n’ont pas de document complet ni de second conteneur extérieur : leur contenu est inséré dans un header/footer existant.

## 4. Formulaire de connexion : les attributs à distinguer

| Attribut | Ce qu’il fait | Ce qu’il ne fait pas |
| --- | --- | --- |
| `for` du label | Référence l’ID d’un champ ; cliquer sur le label lui donne le focus. | Ne nomme pas les données envoyées au serveur. |
| `id` de l’input | Identifie le champ dans le document. | Ne remplace pas son `name`. |
| `name` | Donne la clé des données lors d’une future soumission. | N’affiche pas le label. |
| `type="password"` | Masque visuellement les caractères. | Ne chiffre pas la valeur. |
| `autocomplete` | Indique la nature du champ au navigateur et au gestionnaire de mots de passe. | N’implémente pas une connexion. |
| `required` | Participe à la validation native lors d’une soumission normale. | Ne remplace pas la validation côté serveur. |
| `method="post"` | Prévoit des données dans le corps de la requête. | Ne remplace pas HTTPS. |
| `disabled` | Désactive le bouton de soumission de cette maquette. | Ne constitue pas un contrôle de sécurité côté serveur. |

Le formulaire ne possède pas encore de destination `action`. Sans cet attribut, une soumission viserait la page courante ; ce n’est pas une route d’authentification. Ne pas activer le bouton avant de mettre en place le traitement adapté. Utiliser des valeurs fictives pendant les essais. Les classes de formulaire existent, mais leurs styles spécifiques ne sont pas encore écrits.

## 5. CSS mobile-first et facilement modifiable

Nous partons des petites largeurs. Le contenu occupe l’espace disponible, avec une limite de largeur sur les grands écrans. Les listes de tags et les actions reviennent à la ligne avec `flex-wrap`. Aucune media query n’a encore été nécessaire ; une future adaptation sera ajoutée lorsque le contenu le justifiera.

Les propriétés personnalisées dans `:root` centralisent les choix provisoires. `var(--color-surface)` utilise la valeur correspondante. Modifier cette variable change toutes les surfaces qui y font référence : header, footer, cartes et bouton secondaire. Si la direction artistique demande des différences, introduire des variables spécifiques à ce moment-là.

`rem` dépend de la taille racine du texte (habituellement 16 px par défaut). `em` dépend de la taille de police de l’élément. `padding` espace à l’intérieur ; `margin` espace à l’extérieur ; `gap` espace entre les enfants d’un conteneur flex.

Le sélecteur partagé `.site-header__inner, .site-footer__inner` contient une virgule : appliquer la même règle aux deux éléments. Sans virgule, l’espace indique une relation de descendant et la règle ne cible plus nos conteneurs séparés.

Le footer reste après le contenu. Un vide en dessous sur un écran haut est un choix provisoire de mise en page. Nous avons reporté la solution de page d’au moins une hauteur de viewport avec `main` extensible. Aucune hauteur forcée ni position fixe ajoutée.

## 6. JavaScript : comprendre la recette réutilisable

Une déclaration définit la fonction ; un appel l’exécute. `containerId` et `filePath` sont les paramètres déclarés. Les chaînes fournies dans chaque appel sont les arguments. Sans guillemets, un nom de variable représente sa valeur ; avec des guillemets, c’est du texte littéral.

Chaque appel possède ses propres variables. Le premier appel peut attendre le réseau pendant que le second démarre ; ils ne dépendent pas de leur ordre de fin.

`const` interdit de réaffecter la variable, mais on peut modifier l’élément référencé. `!` inverse une valeur logique ; pour notre recherche, `!container` signifie « aucun élément trouvé ». `return` arrête cet appel.

`fetch` retourne une Promise, c’est-à-dire un résultat futur. `await` suspend la suite de la fonction asynchrone, pas toute la page. La réponse HTTP est un objet ; il faut ensuite lire son contenu avec `response.text()`. Une réponse 404 ne fait pas échouer automatiquement `fetch`, d’où le contrôle `response.ok` et l’erreur levée explicitement.

`innerHTML = html` remplace le contenu, il ne l’ajoute pas à la suite. C’est pourquoi on ne voit pas deux logos : le fallback apparaît d’abord, puis le fragment le remplace. En cas d’échec avant ce remplacement, le fallback demeure. Le contenu inséré provient uniquement de fichiers du projet contrôlés ; ne pas y injecter des données utilisateur non vérifiées.

Le document [javascript_header.md](javascript_header.md) développe ces notions plus lentement. Sa section 13 présente la version réutilisable actuelle.

    const response = await fetch(filePath);

    if (!response.ok) {
      throw new Error(`Erreur HTTP : ${response.status}`);
    }

    const html = await response.text();
    container.innerHTML = html;
  } catch (error) {
    console.error(
      `Impossible de charger le fragment : ${filePath}`,
      error
    );
  }
}

loadPartial("site-header", "includes/header.html");
loadPartial("site-footer", "includes/footer.html");
